# 代码库结构（可运行的示例 monorepo）

> 可选模块：用户选择 `--code <目录名>` 时，从 `templates/_code/` 生成独立代码仓。
> 示例栈为 Python 3.12+、uv workspace、FastAPI、SQLAlchemy(async)、Alembic、pytest、React、TypeScript、Vite、pnpm。默认 SQLite 保证开箱即测，PostgreSQL 通过环境变量切换。换栈时保留分层与真实门禁，替换实现。

## 1. 总览

```text
<代码库目录>/                 ← 独立 git，外层知识库整行忽略
├── AGENTS.md                 ← 工程规则
├── 进度记录.md                ← 滚动接续提示＋标记区历史日志
├── README.md / Makefile      ← 真实命令入口
├── pyproject.toml            ← uv workspace：apps/* + packages/*
├── package.json / pnpm-workspace.yaml
├── .env.example              ← 只有非秘密示例；真实 .env 被忽略
├── apps/web-service/
│   ├── pyproject.toml / alembic.ini
│   ├── app/
│   │   ├── main.py           ← 应用装配
│   │   ├── api/              ← 参数与响应，不写业务
│   │   ├── service/          ← 业务逻辑
│   │   ├── model/            ← ORM 与数据访问
│   │   ├── schema/           ← 请求/响应边界
│   │   ├── core/             ← 配置、数据库连接
│   │   ├── exception/        ← 统一错误响应
│   │   └── constants/
│   ├── migrations/           ← Alembic，含 env 与 revision 模板
│   └── test/
│       ├── unit/             ← 无外部服务
│       ├── integration/      ← ASGI 边界与异常响应
│       └── e2e/              ← 启动 uvicorn，真实 HTTP 请求
├── packages/                 ← 只有真正复用时才新增包
├── web/admin/                ← React 健康状态页，可构建、可 lint
├── docker/ / docs/ / scripts/
└── keys/                     ← 本地密钥，git 忽略
```

## 2. 分层铁律

1. 调用方向 `api → service → model`，禁止反向和 api 直摸 model。
2. 外部进出一律过 schema，ORM 模型不外漏。
3. 配置、连接、认证、中间件归 core，不散落业务层。
4. 业务异常由全局处理器转统一错误响应，内部连接串不回显。
5. 只被一处使用的逻辑留 app，不提前抽象进 packages。
6. 文档宣传的每个命令必须存在于 Makefile 并可执行；不能用空目录或占位测试冒充完成。

## 3. 质量门禁

- `make install` 安装 workspace 与前端依赖。
- `make test` 跑 unit＋integration＋真实 HTTP e2e，分支覆盖率阈值 80%。
- `make lint` 跑 Ruff 与 oxlint；`make build` 做前端生产构建。
- 测试数据固定并由测试自造，不依赖本机数据库内容或排序。
- `make db-upgrade` 执行 Alembic；新表/字段必须有明确迁移，不能靠手工改库。
- 测试失败要报告根因，不能删断言、换成占位测试或降低阈值来“变绿”。

## 4. 发布口径

PR 合入 main → 构建不可变制品 → 测试环境验收 → 人工卡点 → **同一制品**晋升生产。生产不得重新构建或另起代码版本；默认递增 patch，minor/major 只用于明确大版本。实际部署流水线由代码仓自己维护，知识库 `publish.sh` 不部署代码。

## 5. 人机协作与分支

- AI 不自行 commit/push；门禁跑绿后停在工作区，等用户验收或明确授权。
- 新增目录/文件先说明用途，避免无边界扩张。
- 动手前分别确认知识库和代码仓当前分支；代码仓可采用自己的功能分支/PR 流程。
- 功能变更先改 `docs/` 对应开发计划再动代码，业务事实仍归上级知识库。
- PR 合并后 pull 校验、复跑门禁、从最新 main 重建分支；删除远端分支后必须实际查询验证。

## 6. 工程进度防腐

`进度记录.md` 不是第二个 AGENTS，也不是终端转储：

- 顶部“新会话接续提示”滚动重写，只留当前阶段、下一步和入口。
- `PROGRESS_LOG` 标记区内每条日志一行，包含日期、事项和操作人。
- 超 50 条运行 `bash scripts/archive-progress.sh`，旧条目移入 `docs/进度历史/`，顶部接续不动。
- 大段测试/部署输出只留摘要和制品指针，避免“行数不多但单文件数百 KB”。

## 7. 与知识库的分工

| 内容 | 住哪 |
|---|---|
| 业务事实、决策、问题、风险、对接口径 | 上级知识库 |
| 工程规则、架构、命令、门禁、发布流程 | 代码库 AGENTS.md / docs |
| 工程进度明细 | 代码库 `进度记录.md` |
| 工程进展一句话摘要＋指针 | 知识库 STATUS.md |
