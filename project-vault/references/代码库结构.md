# 代码库结构（蒸馏自实战 monorepo）

> 本文是 project-vault 的**可选模块**：初始化时用户选择"生成代码库骨架"，AI 按本文建结构，并从 `templates/_code/` 生成代码库自己的 `AGENTS.md` 与 `.gitignore`。
> 示例栈为 **Python 3.14 + uv workspace + FastAPI + SQLAlchemy(async) + PostgreSQL + Alembic + pytest**，前端 pnpm workspace。换栈时**保留分层思想、替换实现**。

## 1. 总览

```
<代码库目录>/                 ← 住在知识库文件夹内，独立 git 仓库（知识库 .gitignore 排除它）
├── AGENTS.md                 ← 工程规则（AI 进代码目录的入口，与知识库 AGENTS.md 各管各的）
├── 进度记录.md                ← 工程明细进度（知识库 STATUS.md 只记摘要＋指针）
├── Makefile                  ← 常用命令统一入口（make dev / make test / make db-upgrade …）
├── pyproject.toml + uv.lock  ← uv workspace 根，工作区成员 = apps/* + packages/*
├── Dockerfile
├── apps/
│   └── web-service/          ← 主后端服务（多服务时并排加 app）
│       ├── app/
│       │   ├── main.py       ← 应用入口：注册路由、中间件、异常处理器
│       │   ├── api/          ← 路由层：只做参数解析与响应，不写业务
│       │   ├── service/      ← 业务逻辑层
│       │   ├── model/        ← 数据访问层（ORM 模型，多对多关联放 association/）
│       │   ├── schema/       ← 请求/响应模型（Pydantic，内外边界）
│       │   ├── core/         ← 基础设施：配置、数据库引擎、认证、中间件
│       │   ├── exception/    ← 异常定义与全局处理器（统一错误响应）
│       │   └── constants/    ← 常量
│       ├── migrations/       ← Alembic 迁移（容器启动自带 upgrade head）
│       └── test/
│           ├── unit/         ← 单元测试
│           ├── integration/  ← 集成测试
│           └── e2e/          ← 端到端测试
├── packages/
│   └── <项目>-utils/          ← 共享工具包（认证、上传、文件处理等可复用模块）
├── web/                      ← 前端（admin 管理端、h5-* 用户端，pnpm workspace）
├── docker/                   ← 部署编排
├── docs/                     ← 工程文档（开发计划、接口文档；业务需求在知识库，不在这里）
├── keys/                     ← 本地密钥/证书（必须在代码库 .gitignore 里）
└── scripts/                  ← 工程脚本
```

## 2. 分层铁律（换什么栈都成立）

1. **调用方向单一**：`api → service → model`，禁止反向、禁止跨层（api 直接摸 model）。
2. **schema 做内外边界**：外部进出一律过 schema，ORM 模型不外漏。
3. **基础设施归 core**：配置、连接、认证、中间件不散落在业务里。
4. **异常统一**：业务抛领域异常，全局处理器统一转错误响应。
5. **可复用的才进 packages**：只被一处用的逻辑留在 app 内，不提前抽象。

## 3. 质量门禁（实战经验值）

- `make test` 全量测试 + 覆盖率阈值 **80%**（utils 包可更高），红了不合并。
- lint（ruff / oxlint）零错误才算完。
- **测试数据单一来源**：钉死在仓库内的测试数据文件（如 walk_test_data.json），禁止从 DB 排序结果等环境相关渠道取测试数据（实战教训：本地与测试服 collation 不同导致填充不一致）。
- 迁移随部署自动执行（容器启动 `alembic upgrade head`），新列/新表随容器落地。

## 4. 发布口径（实战拍板 D-26 的通用化）

- **Commit 保证技术追踪，`vX.Y.Z` 便于阅读**：PR 合入 main → 自动构建 `main-<Commit>` → 测试服部署验收 → 人工卡点 → **同一构建产物**晋升生产，Header 显示 `vX.Y.Z-test` / `vX.Y.Z-prod`＋更新记录。
- 生产**不得重新构建**或另起代码版本；默认递增 patch，minor/major 仅用于明确的大版本调整。
- 流水线串行构建镜像（教训：构建系统与部署系统赛跑会超时）。

## 5. 人机协作纪律（可裁剪，源自实战教训）

- **AI 不自行 `git commit` / `git push`**：代码写完、门禁跑绿后停在工作区，人验收后自己提交或明说"提交"。
- **新增文件先问**：结构里没有的文件/目录，AI 不得自行创建，先问经同意再加（防止项目失控）。
- **动手前确认当前分支**（曾在旧分支上改需求导致返工）。
- PR 走固定流程：描述固定结构（概述＋分模块变更＋有意偏离说明＋测试与门禁＋合并/部署注意）、合并后 pull 校验＋重建开发分支＋清理。
- 需求源先行：页面/功能需求变更，先改 docs/ 下的开发计划再动代码，不许代码先行、计划漂移。

## 6. 与知识库的分工

| 内容 | 住哪 |
|---|---|
| 业务事实、决策、问题、风险、对接口径 | 知识库（project-vault 生成的那套） |
| 工程规则、架构说明、命令、门禁、发布流程 | 代码库 `AGENTS.md` |
| 工程进度明细（commit、MR、部署实况） | 代码库 `进度记录.md` |
| 工程进展一句话摘要＋指针 | 知识库 `STATUS.md` |
