# 架构演进：项目、公司与代码仓

> 本文解决“库长大之后怎么变”，不替用户自动迁移旧库。迁移必须单独确认范围、备份和验收。

## 1. 先分清信息属主

| 信息 | 唯一归口 |
|---|---|
| 单个项目的需求、方案、决策、问题、风险、依赖 | 该项目知识库 |
| 跨项目仍有效的组织、制度、公司账号与共享资料 | 公司级库或公司级分区 |
| 工程架构、命令、测试、发布与部署实况 | 对应代码库 |
| 当前工程一句话摘要与指针 | 项目知识库 `STATUS.md` |

同一事实只在一个属主处维护，其他地方引用编号或相对链接。不要为“看起来集中”复制全文。

## 2. 从项目库演进到公司级库

项目库出现多个独立业务项目时，不要再让所有项目共用一个 Q/R/E/D/F 上界。推荐两种形态：

- **项目不多且仍各自独立**：每项目一个完整 project-vault，公司级共享信息另建公司库，项目主页只放公司库指针。
- **确需同库管理**：公司根库管理公司级信息；`50_业务/<项目>/` 内每项目保留自己的 AGENTS/STATUS/CHANGELOG/REGISTRY 和归口文件。每个编号只在所属项目作用域唯一；根库校验必须按项目分别执行，不能把其他项目的 Q1 当成本项目悬空引用。

公司根库可以有公司级决策，但必须与项目编号分作用域。不要直接把单项目 REGISTRY 改成多项目共享流水号：这会让归口、归档和项目拆分都失去边界。当前生成器只生成单项目库；上述演进是独立迁移工作，不在初始化时静默完成。

## 3. 多代码仓与历史仓

- 每个活跃代码仓都是独立 git 仓库，外层知识库必须按整行目录规则忽略它。
- 活跃、历史、参考仓在 `00_项目主页.md` 分别登记“用途、是否维护、工程入口”；历史/参考仓不得被误认为当前实现。
- 历史代码、备份 bundle、参考成品不复制进知识文档；只留位置与用途。大文件是否需要远端保存另行决定。
- 进入任何代码目录先读该仓自己的 AGENTS.md；知识库规则不能覆盖代码仓更具体的工程规则。

## 4. 分支模式

`vault.conf` 是分支模式唯一来源：

- `single`：适合纯本地或单人简流程，`main` 是日常工作分支；提交和推送仍需用户明确授权。
- `dual`：`main` 是已发布真相，`feat/next` 是唯一编辑工作区。日常改动、快照都只发生在 `feat/next`；只有显式发布才把其合入 `main`。

代码仓可以选择自己的功能分支/PR 流程，不必照搬知识库模式；动手前必须分别确认知识库与代码库当前分支。禁止用强推、重置或删除分支来“修复”普通校验失败。

## 5. 快照、提交、发布不是一回事

- **快照**：保存工作区，先体检再提交；默认不推送。
- **正式提交**：用户明确要求后，按仓库约定提交；不能由定时任务冒充。
- **发布**：仅 dual 模式，显式确认后将已校验的 `feat/next` 合入 `main` 并同步两端；它不是代码部署。
- **代码部署**：由代码仓自己的工程流程负责，知识库发布不得触发或替代它。

## 6. 旧库升级

1. 先备份并记录当前 project-vault 版本、定制脚本和链接语法。
2. 只比较并选择性采用新脚本；不得整目录覆盖旧库，尤其不能覆盖项目自己的 publish/private/custom 校验。
3. 模板只用于新增缺失归口，不覆盖已有内容文件。
4. 在非生产副本验证取号、双校验、快照与分支保护后，再升级真库；新克隆用 `scripts/install-hooks.sh` 恢复本地门禁，已有自定义钩子不覆盖。
5. 旧 wikilink、D-01 等历史格式需要显式兼容或单独迁移，不能直接套新格式校验后强行修数。
