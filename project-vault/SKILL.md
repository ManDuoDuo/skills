# project-vault · 项目知识库架构 Skill

> 版本 v1.0 ｜ 建立 2026-10-19 ｜ 蒸馏自一个真实运转的单人项目库（文档＋代码＋商务材料混合）的实战教训。
> 本文写给执行初始化的 AI 看，也写给后续评审/优化本 Skill 的 AI 看：每条规则都标注了"为什么"，改规则前先读懂动机。

---

## 0. 这是什么，解决什么问题

一套**项目知识库的生成器 + 运行规范**。解决的核心矛盾：

**AI 没有跨会话记忆，而项目会跑几个月。** 项目的所有事实、决定、口径、开放问题必须沉淀在文件里，并且这套文件要能经受"每天往里加东西、连加数月"而不腐坏、不膨胀、不失联。

适用场景：单人或小团队、需要 AI 长期陪跑的项目（需求解读、方案设计、合规判断、外部对接、推进跟踪）。
不适用：纯代码仓库（代码库有自己的 AGENTS.md 即可）、一次性短任务。

本 Skill 做三件事：

1. **生成**：把任意空文件夹初始化为结构完整的知识库（§4 流程）。
2. **立规**：生成的 `AGENTS.md` 是之后所有 AI 会话在该库里的行为准则（§5 是它的设计依据）。
3. **防腐**：内置机制保证库可无限累加而不爆（§2.1、§5.4）。

---

## 1. 五条宪法（一切规则的源头，生成的 AGENTS.md 里也有，这里是完整版）

1. **文件是唯一记忆** —— 没落盘 = 不存在。用户确认的任何事实/决定/口径，必须写入库内文件；不要回问"要不要记下来"，默认记。
2. **唯一归口** —— 同类信息只有一个文件。新信息**并入**旧文件；新信息推翻旧结论时，**回去改旧结论本身**，禁止新建"解读-xxx.md"式碎片文件，禁止在原地打补丁式追加一段矛盾的话。
3. **编号注册表** —— 开放问题 `Q`、风险 `R`、外部依赖 `E`、决策 `D`、功能需求 `F`，五类编号各有归口文件，一律从 `REGISTRY.md` 取号，**不复用、不跳号**。跨文件引用用编号（"见 Q12"），不复述内容——编号即事实的指针。
4. **入口分层** —— `AGENTS.md`（AI 入口，只放规则）→ `STATUS.md`（当前状态，一屏）→ `00_项目主页.md`（文件地图）→ 各归口文件。任何新会话按固定清单读 3～5 个文件即可开工，**不允许反问用户背景**。
5. **防腐机制** —— 唯一允许"长胖"的文件是 `CHANGELOG.md`（追加式日志），超 50 条自动归档；两个必读文件（AGENTS、STATUS）从结构上没有变胖的通道；每次大改后跑断链校验。

## 2. 关键架构决策（以及为什么——评审时重点看这里）

### 2.1 三文件分职：AGENTS / STATUS / CHANGELOG

**教训来源**：初代设计把"规则＋当前状态＋变更记录"全塞进一个 AGENTS.md。结果它一路长到 32KB，撑爆了 AI 每次会话的读取预算（这个文件是每会话必读的），被迫两次人工抢救式归档。

根因：三种**变化频率完全不同**的内容共用一个文件——规则几乎不变，状态天天变，日志只增不减。

解法：

| 文件 | 内容 | 更新方式 | 会变胖吗 |
|---|---|---|---|
| `AGENTS.md` | 规则、约定、铁律、角色上下文、材料流水线 | 只在规则变化时改，**禁止往里追加状态或日志** | 不会，目标 ≤ 90 行（v1.4 起含角色表与流水线，仍是纯规则无状态） |
| `STATUS.md` | 当前状态：阶段、焦点问题、最近决策、建议阅读 | **滚动重写**：更新时直接改旧格子，不保留"以前是什么" | 不会，永远一屏 |
| `CHANGELOG.md` | 变更日志：日期＋改了什么 | 追加式，最新在最下 | 会 → 超 50 条由脚本归档最旧部分到 `99_附件/历史/` |

"历史去哪了"：状态的演变史 = CHANGELOG；文件的演变史 = git（见 2.4）。

### 2.2 位置无关：模板零绝对路径

知识库会被整体搬迁（换电脑、换系统、换盘符）。因此：

- 库内文件互相引用**一律用相对链接**：`[决策记录](30_合规与决策/决策记录.md)`；
- 任何文件内容里**不得出现** `/Users/...`、`D:\...` 这类绝对路径；
- 初始化只问"作用于哪个文件夹"，默认当前目录，路径含中文/空格都合法。

### 2.3 相对 Markdown 链接，拒绝工具私有语法

`[[wikilink]]` 双括号语法只有 Obsidian 认识——换 VS Code、上 GitHub、用静态站生成器，全部变成死文本。标准 `[文字](路径.md)` 在**包括 Obsidian 在内的所有工具**里都可点击。

Obsidian 用户一次性设置即可无缝：设置 → 文件与链接 → 链接格式 = "尽可能 shortest path/相对路径"。`.obsidian/` 目录只是该工具的本地配置，不属于架构，不入 git 也无妨。

### 2.4 双层 git：知识库与代码库同住一个项目文件夹，各录各的

项目通常既有文档库又有代码库。结构：

```
<项目文件夹>/            ← 知识库（git 仓库 A，本 Skill 初始化时建）
├── .git/                ← 录像机 A：录文档。`.gitignore` 排除代码子目录
├── AGENTS.md  STATUS.md  ...  99_附件/
└── <代码库目录>/         ← 代码（git 仓库 B，工程团队/工程会话自己管）
    ├── .git/            ← 录像机 B：只录代码
    └── AGENTS.md        ← 代码库自己的工程规则（测试门禁、发版流程……）
```

要点：

- **两套 AGENTS.md 各管各的**：知识库的管"记忆怎么记"，代码库的管"代码怎么写"。AI 进代码目录读代码那份，谈业务读知识库这份。
- **进度两层记法**：知识库 `STATUS.md` 只记"工程进展一句话摘要＋指针"；工程明细（commit、MR、部署实况）留在代码库自己的进度文件里。两边不重复记同一件事。
- 外层仓库的 `.gitignore` 必须排除代码子目录，否则 git 会把它当 submodule/gitlink，纠缠不清。模板 `.gitignore.tmpl` 里留了注释行，初始化后由用户填上真实目录名。
- **历史代码不进新库**：老代码、参考架构、备份 bundle 这类东西一律留在库外归档处，知识库里写一行指针即可。新库从第一天保持清爽。
- **代码骨架是可选模块**：初始化时用户若选择生成代码库，按 [references/代码库结构.md](references/代码库结构.md) 建分层 monorepo 骨架（蒸馏自实战：uv workspace、`api→service→model` 分层、三层测试、覆盖率门禁、同制品晋升发布口径），并从 `templates/_code/` 生成代码库自己的 AGENTS.md。知识库 Skill 主体保持技术栈无关，换栈时只换 `_code` 模板与该参考文档。

### 2.5 敏感信息只存指针

密码、密钥、证件号、合同金额细节等，一律**不写明文**，只写存放位置（"见 1Password 的 xx 条目""见某加密盘"）。这是知识库日后上云端私有仓的前提条件，也是给 AI 划的明确红线——AI 不需要知道秘密本身才能干活。

### 2.6 公司级与项目级分层

组织架构、制度、公司账号这类**公司级**信息不随任何单一项目走。本 Skill 只生成**项目库**；公司级信息由用户在 `00_项目主页.md` 里用指针指向既有公司库（项目多了以后可抽成独立公司 vault，那是另一个决定，不在初始化时替用户做）。

### 2.7 脚本是加速器，不是必需品

`scripts/` 下五个日常脚本（取号、断链校验、编号对账、日志归档、提交门禁）只是 macOS/Linux/git-bash 上的快捷方式。**每件手工操作的等价步骤都写在 §5**，任何 AI 在任何系统（含 Windows 无 bash 环境）上徒手读写文件都能完成同样的事。脚本不可用 ≠ 能力缺失。另有 `selftest.sh` 是本 Skill 自身的回归测试（改任何脚本/模板后必跑），不拷进生成的库。

## 3. 生成出来的库长什么样

```

├── CHANGELOG.md             ← 变更日志：追加式，超 50 条脚本归档
├── REGISTRY.md              ← 编号上界：Q/R/E/D/F，唯一来源
├── 说明.md                  ← 人类入口：这个库是什么、怎么用
├── 00_项目主页.md            ← 文件地图＋编号约定＋开场清单
├── .gitignore               ← 若启用 git
├── 10_需求/
│   ├── 原文/                ← 需求材料原文，只进不改
│   └── 白话全解.md          ← 需求解读唯一主文档（全局线＋进度表＋逐段解读）

├── 30_合规与决策/
│   ├── 主体档案.md          ← 涉及哪些公司/团队，各干什么
│   ├── 合规红线.md          ← 不能越的线及依据
│   └── 决策记录.md          ← D 类编号归口
├── 40_推进/
│   ├── 待确认问题清单.md     ← Q 类编号归口
│   ├── 待办与风险.md        ← R 类编号归口
│   └── 依赖与对接清单.md     ← E 类编号归口
├── 90_模板/                 ← 写作骨架：决策/问题/纪要/文件头尾
├── 99_附件/
│   ├── 清单.md              ← 原件索引
│   └── 历史/                ← 归档区（CHANGELOG 旧段、失效文件）
```

## 4. 初始化流程（AI 逐步执行）

**触发**：用户说"用 project-vault 初始化这个文件夹/建项目库"，并打开或指定了目标文件夹。

**Step 0 · 确认目标文件夹**
默认 = 当前工作目录。检查：若不存在则创建；若**非空**（除 `.DS_Store` 外有内容），列出将新增的文件清单，**请用户确认后再继续**；同名文件已存在的一律跳过不覆盖，并向用户报告跳过了哪些。

**Step 1 · 问用户四个问题**（一次问完，别挤牙膏；第 4 个可选）：
1. 项目名称（用于各文件标题，替换 `{{PROJECT_NAME}}`）
2. 一句话说明这个项目是什么（替换 `{{PROJECT_DESC}}`）
3. 是否启用 git 本地版本记录（**建议启用**；远端备份以后随时可加，不在此问）
4. 是否同时生成代码库骨架（要的话给目录名，如 `backend`；不要就是纯文档库，以后随时可补）

**Step 2 · 生成**（二选一）：
- 有 bash：跑 `scripts/init-vault.sh <目标目录> <项目名> ["简介"] [--git] [--code <目录名>]`（脚本在本 Skill 的 scripts/ 下，它会自动复制模板、替换占位符、拷贝工具脚本、可选生成代码骨架、可选 git init）；
- 无 bash：手工执行等价步骤——把 `templates/` 下（除 `_code/` 外）每个 `.tmpl` 复制到目标目录对应位置、文件名去掉 `.tmpl`、内容中 `{{PROJECT_NAME}}`/`{{PROJECT_DESC}}`/`{{DATE}}`/`{{VAULT_VERSION}}` 替换为实际值（版本戳见 init-vault.sh 顶部 `VAULT_VERSION`）；普通文件（`90_模板/`、`.gitignore.tmpl` 等）原样拷贝（`.gitignore.tmpl` 更名为 `.gitignore`，**无条件复制**，与是否启用 git 无关）；创建空目录 `10_需求/原文/`、`99_附件/历史/`；把本 Skill `scripts/` 下五个日常脚本（不含 init-vault.sh / selftest.sh）拷入目标 `scripts/`；启用 git 则执行 `git init && git add -A && git commit -m "建库"`，并把提交门禁 shim 写进 `.git/hooks/pre-commit`（内容就一行：`exec bash "$(git rev-parse --show-toplevel)/scripts/pre-commit.sh"`，chmod +x）。**若生成代码骨架**：按 [references/代码库结构.md](references/代码库结构.md) 的目录树建空目录，从 `templates/_code/` 生成代码库的 `AGENTS.md`（替换占位符）与 `.gitignore`，新建 `进度记录.md`；把代码目录追加进知识库 `.gitignore`；在 `00_项目主页.md` 第三节登记；启用 git 时在代码目录内单独 `git init` 并首次提交。

**Step 3 · 自检**：跑（或手工等价执行）`check-links.sh`，确认生成的库零断链。

**Step 4 · 教用户开口**：告诉用户——"库建好了。以后任何 AI 会话打开这个文件夹，说'读 AGENTS.md，我开始发材料了'即可。有代码的话把代码库放进来当子目录，并在 `00_项目主页.md` 登记。"

## 5. 日常运作（AI 维护这个库时的规矩）

### 5.0 材料录入流水线（最高频日常，生成的 AGENTS.md §六也有同款）

用户发来材料（录音转写/带批注合同/截图/口头口径/文档）时，按固定顺序动七个文件：
① 原件入 `99_附件/` 并在清单登记 → ② 解读续写进白话全解对应章节（三段式）→ ③ 新发现当场取号进 Q/R/E/D 归口 → ④ 全局线被验证/推翻则改那条线本身 → ⑤ 有新文件则同步项目主页地图 → ⑥ STATUS 焦点格更新（编号＋一句话）→ ⑦ CHANGELOG 追加一行（含操作人）。
源库教训：这条流水线以前靠 AI 记着，漏步是常态（解读写了、编号没取；附件收了、清单没登）。写成固定步骤后按单执行，不靠自觉。

### 5.1 登记新编号（Q/R/E/D/F）
- 脚本：`bash scripts/next-id.sh Q` → 输出 `Q1` 并自动把 REGISTRY 上界 +1。
- 手工等价：读 `REGISTRY.md` 对应行 → 数字 +1 → 写回该行 → 在归口文件里使用新编号。**取号和写回必须是同一轮动作**，防止"用了号忘了改上界"导致重号。

### 5.2 断链校验
- 脚本：`bash scripts/check-links.sh`。
- 手工等价：grep 所有 md 里的 `](xxx)` 相对链接，逐个确认目标文件存在；发现 `[[wikilink]]` 语法要警告（本库用标准相对链接）。
- 时机：每次新增/改名/移动文件后。

### 5.3 写文件的固定动作
- 每个内容文件顶部维护"更新日期"；
- 新增/移动/删除文件后，同步 `00_项目主页.md` 的文件地图；
- 实质改动在 `CHANGELOG.md` 追加一行（日期＋改了什么）；
- 单文件**不再手写变更记录**（那是没有 git 时代的 workaround，git 已承担）。

### 5.4 CHANGELOG 归档
- 脚本：`bash scripts/archive-changelog.sh`（超 50 条时把最旧部分搬到 `99_附件/历史/CHANGELOG-归档-<时间戳>.md`）。
- 手工等价：数条目数 → 超 50 则把最旧的 (总数−50) 条剪出，存为上述归档文件，CHANGELOG 保留固定头和最新 50 条。
- 时机：每次追加日志时顺手检查。

### 5.5 Windows / 无 bash 环境
四个脚本都可用 §5.1/5.2/5.4/5.6 的手工等价步骤替代。路径分隔符、中文文件名、空格都要兼容；不要假设 `python`/`sed` 存在，用 AI 自身的文件读写能力完成。

### 5.6 编号对账
- 脚本：`bash scripts/check-registry.sh`。
- 三件事：① REGISTRY 上界 ≥ 归口文件实际最大编号（漂移=错误，手工取号久了必发生）；② 被引用的编号都已登记（悬空引用=错误）；③ 登记的编号在归口文件之外有引用（死编号=警告，不阻塞）。
- 手工等价：grep 归口文件里的编号、grep 全库引用、肉眼比对三份清单。
- 时机：每次会话收尾时（见 5.7）。

### 5.7 会话收尾清单
宪法第一条的风险窗口在会话结束前——结论还在对话里没落盘，窗口一关就没了。生成的 AGENTS.md §六有同样清单，收尾按序：① 口头结论全部落盘 → ② 滚动重写 STATUS.md → ③ CHANGELOG 追加一行 → ④ 跑 check-links + check-registry。

### 5.8 项目终态
项目都会完结。完结仪式（防止"不敢删又没人读"的僵尸库）：
1. STATUS.md 改写为「已完结（日期）＋一句话结局＋关键结论落在哪些文件」；
2. CHANGELOG.md 追加完结一行；git 打 tag（如 `archive/完结-YYYY-MM-DD`）；
3. AGENTS.md 开场清单前加一行「本库已完结，只读」；
4. 库可整体移至归档位置，但**不删**——它是后来项目的判例库。

### 5.9 自动快照（可选）
把"收尾靠自觉"再兜一层底：由 AI 工具的定时任务每晚调用 `bash scripts/snapshot.sh`——工作区有变化才提交（`快照:` 前缀，与正式提交区分），随后自动跑双校验并汇报异常。
- **属主唯一原则**：定时器不随 skill 走，属宿主 AI 工具（每家有自己的调度器）。一个库同一时间只能有一个调度器属主，属主是谁记在该库 AGENTS.md 变更记录里——换工具接管时先撤旧装新，防止双快照互踩。
- 手动等价：`git status` 有变化 → `git add -A && git commit -m "快照: <日期>"` → 跑双校验。

## 7. 模板与占位符约定

- 模板统一放在本 Skill 的 `templates/`，与目标库的目录结构一一对应；`templates/_code/` 是代码库专用模板（代码库的 AGENTS.md、.gitignore），只在生成代码骨架时使用；
- 占位符四个：`{{PROJECT_NAME}}`（项目名）、`{{PROJECT_DESC}}`（一句话简介）、`{{DATE}}`（初始化当天，YYYY-MM-DD）、`{{VAULT_VERSION}}`（生成器版本戳，值见 init-vault.sh 顶部 `VAULT_VERSION`，改格式约定时必须同步升版）；
- `90_模板/` 下的文件是给**日常使用**的写作骨架（登记新决策/新问题时照抄），不含占位符，原样拷贝；
- 新增模板时：保持"零绝对路径、相对链接、占位符只用上述四个"的约束。
- ⚠️ **新增占位符的第一件事：过 `esc()`**。凡是"用户输入进 sed 替换串"的位置都是同一病灶——`\` `/` `&`（以及换分隔符后的 `|`）在 sed replacement 里是特殊字符，用户输入里带一个就全崩。这类坑已连出三次（项目名/简介、变量名、CODE_DIR）才封口，成本远高于预防。脚本里的范式：`FOO_E="$(esc "$FOO")"`，替换一律用转义后的 `_E` 变量；新增入口时照抄，不要事后补。

## 8. 明确不做的事（边界）

- **本 skill 是跨项目通用工具**：任何"为某个具体项目/业务/技术栈服务"的内容不得进入知识库主体；模板与文档里的示例一律用中性词（`backend/`、`my-app` 这类），不得出现真实项目名。技术栈相关内容只允许存在于明确标注"示例栈、换栈保留分层思想"的可选模块（代码骨架）；项目级流程（发版、口令、话术）一律不长进 skill，留在各项目自己的库或项目级 skill 里生长——skill 服务"很多个项目"，不服务任何一个。
- 不生成公司级目录（组织/制度/账号）——见 §2.6；
- 不配置 git 远端——本地录像机建好即可，上云是用户之后的独立决定；
- 不迁移任何既有老库——老库的改造（装 git、换链接语法）是单独的工作，不夹带进初始化；
- 不内置任何项目级流程 Skill（如某项目的固定发版流程）——项目做久了按需各自生长，见 §2.4 的同住结构。
